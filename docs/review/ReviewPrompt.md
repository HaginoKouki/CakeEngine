# CakeEngine 定期レビュー・ドキュメント整備

## 運用設定

毎回、この節だけをその回の条件に合わせて書き換えてください。

| 項目 | 値 |
| --- | --- |
| レビュー日 | YYYY-MM-DD |
| 前回のレビュー時点 | `docs/review/` にある最新の記録の冒頭に書かれたコミットハッシュ。記録が無ければ「初回」 |
| 作業の進め方 | `claude/review-YYYY-MM-DD` ブランチを作り、変更を 1 つのコミットにまとめる。push と PR の作成は行わない |
| ビルドとテスト | Windows と Visual Studio 2026 がある環境なら Debug と Release をビルドする。できない環境では GitHub Actions の最新の実行結果を確認し、その旨を記録する |
| ソースコードの修正 | 行わない。ソース内のコメントも変更しない |

---

## 目的

CakeEngine の現在の実装・設計・仕様を調査し、ドキュメントの整備とコードレビューを行ってください。

単にコードや機能を列挙するのではなく、初めて CakeEngine のコードを読む開発者が、全体像・各機能の役割・処理の流れ・設計上の意図を理解できる状態にすることを重視してください。

主な目的は次の 4 点です。

1. 設計・構造・仕様を、初めてコードを見る開発者にも理解できるドキュメントとして整理する。
2. 既存の設計方針と現在の実装を比較し、矛盾・仕様漏れ・バグ・保守性の問題をコードレビューとして記録する。
3. 前回のレビュー以降に追加・変更された機能を特定し、実装と既存ドキュメントの差分を確認する。
4. 実装とドキュメントのどちらが正しいか判断できない箇所は、推測で仕様を確定せず「要確認事項」として記録する。

情報を減らして分かりやすくするのではなく、情報の分類・順序・説明方法を工夫して理解しやすくしてください。

## 0. このリポジトリの前提

調査を始める前に、次の構造を頭に入れてください。

| 場所 | 内容 |
| --- | --- |
| `project/Engine/<層名>/` | エンジン本体。Foundation、Platform、Graphics、Asset、Render、Scene、Editor、Application の 8 層。名前空間は `Cake` |
| `project/Game/` | ゲーム固有のコード。`GameModule.cpp` の 2 つの関数でエンジンに接続する |
| `project/Assets/Shaders/`、`project/EngineResources/shaders/` | HLSL。起動時に DXC で実行時コンパイルされる |
| `project/CakeEngine.vcxproj`、`CakeEngine.slnx`、`.github/workflows/` | ビルド構成（Debug と Release、x64）と CI |
| `docs/README.md` | ドキュメントの地図。ここから各ページへ辿る |
| `docs/design/` | 層ごとの設計書と `Overview.md`、`Conventions.md` |
| `docs/guides/` | ビルドと実行、コンポーネントとシェーダーの追加手順 |
| `docs/review/` | レビューの運用（`README.md`）、未解決事項の一覧、各回の記録（`YYYY-MM-DD.md`） |

調査の対象外は `project/externals/`（外部ライブラリ）、`project/Assets/` の素材ファイル（モデル、テクスチャ、`.meta`）、`generated/` です。外部ライブラリは、エンジン側からの使い方が変わった場合だけ確認してください。

## 1. 調査の進め方

### 1.1 既存ドキュメントの確認

次の順に読んでください。

1. `README.md` と `docs/README.md`
2. `docs/design/Overview.md`（層の並び、依存の規則と現状、起動と 1 フレームの流れ）
3. `docs/design/` の各層のページと `Conventions.md`
4. `docs/guides/` の各ページ
5. `docs/review/README.md`（未解決事項の一覧）と、直前のレビュー記録

設計方針、全体構造、各モジュールの役割、命名規則、依存関係を把握し、どの情報をどのページで管理しているかを確認してください。

### 1.2 ソースコードと設定ファイルの確認

`project/Engine/`、`project/Game/`、`project/main.cpp`、HLSL、ビルド設定、CI 設定を調査してください。必要に応じてコミット履歴とヘッダコメントも確認してください。

ファイル名やクラス名だけから機能を推測せず、実際の実装と利用箇所を確認してください。層をまたぐ依存は `#include` を集計して確認し、設計書の「他の層との関係」と突き合わせてください。

### 1.3 前回からの変更の確認

運用設定の「前回のレビュー時点」のハッシュを起点に、`git log <ハッシュ>..HEAD` と `git diff --stat <ハッシュ>..HEAD` で変更を確認してください。

- 追加・変更・削除されたファイル
- 変更されたクラス・関数・API
- 変更による既存機能への影響
- 設計方針や依存関係への影響
- ドキュメントへの反映状況

変更されたファイルだけで調査を終えず、変更の影響を受ける既存コードや呼び出し元も確認してください。変更が無い機能も、全体の設計を理解するために必要な範囲で確認してください。ただし、変更が無いこと自体を問題として扱わないでください。

履歴や前回の記録を確認できない場合は、確認できなかったことを明記してください。ファイルの更新日時や現在のコードだけから変更時期を断定しないでください。

## 2. 実装の調査で見る項目

- 新しく追加された機能
- 既存機能の変更・削除
- クラス・関数・モジュールの責務の変更
- API やインターフェースの変更
- データ構造の変更
- モジュール間の依存関係の変更
- リソース管理・メモリ管理の変更
- エラー処理や例外処理の変更
- 設計方針に影響する変更
- ドキュメントに反映されていない変更

単純なコードの差分だけでなく、その変更によって設計・仕様・利用方法がどう変わるかを重視してください。

## 3. ドキュメントの更新方針

### 3.1 基本原則

ドキュメントは、実装の正確な説明と、設計方針の記録を目的とします。実装されている事実、設計上の意図、推測、未確定事項を混同しないでください。説明を分かりやすくするために、存在しない仕様や設計意図を補ってはいけません。

### 3.2 更新してよいケース

根拠を確認したうえで更新してください。

- 実装が既存の設計方針に沿っており、ドキュメントが古くなっている。
- 新しい機能が追加され、その仕様が実装から明確に判断できる。
- クラス・関数・モジュールの責務が変更され、既存の説明が実態と一致しなくなっている。
- 既存仕様の説明に明確な誤りがある。
- 重要な仕様や依存関係が記載されておらず、開発者の理解に支障がある。
- 説明の順序や構成を改善することで、内容を変えずに理解しやすくできる。

### 3.3 勝手に変更してはいけないケース

次の場合は、仕様を推測してドキュメントを書き換えず、現在確認できる事実を「未実装・要確認」の節とレビュー記録に書いてください。

- 実装とドキュメントのどちらが正しいか判断できない。
- 実装が既存の設計方針に反している可能性がある。
- バグなのか、意図的な仕様変更なのか判断できない。
- コードから設計意図を確定できない。
- 複数の設計方針が考えられ、それぞれに異なる影響がある。
- 仕様変更の承認が必要と思われる。

### 3.4 各ドキュメントの役割

| ドキュメント | 役割 | 更新のしかた |
| --- | --- | --- |
| `README.md` | 初めて見る開発者が最初に読む。何をするエンジンか、どんな構造か、どこを読めば詳しい仕様が分かるか | 機能一覧、構造、フォルダ構成、ビルドの要点、読む順番、開発の状態を実装に合わせて保つ。詳細は `docs/` へのリンクで済ませる |
| `docs/README.md` | ドキュメントの地図 | ページを追加・削除・改名したら必ず更新する |
| `docs/design/Overview.md` | 層の一覧、依存の規則と現状、起動の流れ、1 フレームの流れ、ビルド構成、共通の考え方 | 層をまたぐ変更、初期化順や更新順の変更、ビルド構成の変更があれば更新する |
| `docs/design/<層>Layer.md` | 層ごとの説明。節の順は「この層が担当すること」「配置」「構成」「主要な仕組み」「他の層との関係」「守るべき規則」「未実装・要確認」 | この節構成を保つ。クラスの追加や責務の変更は「構成」と「主要な仕組み」へ、依存の変化は「他の層との関係」へ、実装から確定できない点は「未実装・要確認」へ書く |
| `docs/design/Conventions.md` | 整形、命名、ファイル配置、ヘッダコメント、ビルドフラグ、層をまたぐ設計上の約束 | コードから新しい約束が読み取れたとき、または既存の約束が守られなくなったときに更新する |
| `docs/guides/` | 目的から逆引きする手順書 | 手順に関わる API やファイルが変わったら更新する。コード例は実装と一致させる |
| `docs/review/README.md` | レビューの運用と未解決事項の一覧 | 毎回、未解決事項の状態を更新し、新しいレビュー記録を表に追加する |
| `docs/review/YYYY-MM-DD.md` | その回のレビュー記録 | 第 8 節の形式で新規作成する |

新しいページを作る場合は、既存のページとの重複を避け、`docs/README.md` に置き場所を明記してください。ページを細分化しすぎず、関連する情報は 1 つのページにまとめてください。既存のページ構成を大きく変える場合は、必要性と影響を考え、理由をレビュー記録に書いてください。

### 3.5 書き方

すべてのドキュメントで次の規則を守ってください。

#### 説明の順序

原則として、何のための機能か、どのような役割か、どのような構造か、どのように動作するか、他の機能とどう関係するか、利用時の制約は何か、の順に説明してください。対象に必要のない項目は省略して構いません。

#### 読みやすさ

- 1 つの段落では 1 つの主題を説明する。1 文に複数の重要な情報を詰め込まない。
- 一覧性が重要な情報は表にする。説明文を無理に表へ詰め込まない。
- 略語や専門用語は、初出時に必要に応じて意味を説明する。
- コード例は短く、目的が分かるものにし、現在の実装と一致していることを確認する。
- 同じ内容を複数の場所で繰り返さず、参照リンクを使う。
- 既知の事実と、設計上の推奨や未確定事項を明確に区別する。

#### 文体

- 説明文は「です・ます」で書く。規則の箇条書きは「〜する」「〜しない」で書く。
- 絵文字、文末の全角コロン、ダッシュ記号は使わない。太字は見出しの代わりに使わない。
- 設計書に日付や変更履歴を書かない。履歴はレビュー記録と Git に任せる。
- 「管理する」「処理する」「連携する」「制御する」といった言葉だけで説明を終えず、何を入力に何を行い何を出すか、何を担当し何を担当しないかを具体的に書く。ただし、実装から確認できない処理内容や意図を推測しない。

#### 情報の正確性

- クラス名・関数名・ファイル名は実装と一致させる。
- 実装されている機能と、将来の構想を区別する。
- 実装から確認できない仕様は断定しない。設計意図が不明な場合は、事実と推測を分けて書く。
- ドキュメント内のリンクと参照先が実在することを確認する。

## 4. コードレビューの観点

### 4.1 設計

既存の設計方針との矛盾、責務の逸脱、不自然な依存関係、循環依存、抽象化の不足や過剰、将来的に拡張しにくい設計、モジュール間の結合度や依存方向の問題。

### 4.2 実装

明らかなバグ、未定義動作につながる可能性、メモリ管理とリソース管理の問題、エラーハンドリングの不足、`nullptr` などの不正状態への対応不足、不要な処理、同じ処理の重複、保守性を低下させる実装、入力値やオブジェクトの状態に対する検証不足。

### 4.3 API とインターフェース

利用者にとって分かりにくい API、命名の不整合、引数と戻り値の設計上の問題、意図しない利用方法を許してしまう API、既存 API との一貫性がない変更、利用側に過度な知識や作業を要求するインターフェース。

### 4.4 ドキュメント

実装とドキュメントの矛盾、記載されていない重要な仕様、古くなった説明、誤解を招く説明、コメントと実装の矛盾、README から詳細情報への導線不足、説明の順序や構成による理解のしにくさ、同じ情報の重複や置き場所の不適切さ。

### 4.5 既存設計との整合性

C++ のコーディングスタイル、設計パターン、一般的なベストプラクティスだけを理由に問題と判定しないでください。CakeEngine の既存設計、`Conventions.md` の規約、採用済みの方針、実際の利用方法を優先してください。

既存の設計方針そのものに問題があると考える場合は、現在の方針、その方針によって生じている具体的な問題、問題が発生する条件、改善する場合の利点と欠点、影響を受ける既存コードを明確にしてください。別の設計方法が存在するという理由だけで変更を要求しないでください。

## 5. 指摘の重要度

| 重要度 | 基準 |
| --- | --- |
| Critical | クラッシュ、データ破壊、重大な未定義動作、起動不能、深刻な設計破綻など、早急な対応が必要な問題 |
| High | 現在または近い将来、重大な問題になる可能性が高いもの |
| Medium | 設計・保守性・拡張性に具体的な問題があり、対応を推奨するもの |
| Low | 影響は限定的だが、改善することで保守性や可読性が向上するもの |
| Info | 問題とは断定できないが、設計上の確認や情報共有に価値があるもの |

問題の深刻さ、発生条件、影響範囲、発生可能性を考慮して判断してください。単なる改善提案や好みの違いを Critical や High に分類しないでください。判断材料が不足している場合は重要度を過度に高く設定せず、「要確認」と明記してください。

## 6. 指摘の書き方

読んだ開発者が問題を理解し、修正するかどうかを判断できる内容にしてください。各指摘には、必要に応じて次を記載します。すべてを形式的に埋める必要はありません。

優先度、問題の分類（設計、実装、API、ドキュメント）、対象ファイル、対象箇所（クラス名、関数名、行番号）、確認できた事実、問題の内容、発生する条件、具体的な影響、設計方針との関係、推奨する対応、判断の確実性（確定した問題、懸念、要確認）。

### 根拠の提示

- 可能な限りファイルパスと行番号を示し、行番号が変わる可能性を考慮してクラス名や関数名も併記する。
- 根拠として挙げたコードが、実際に問題の説明を裏付けていることを確認する。
- 設計方針との矛盾を指摘する場合は、根拠となる設計書のページも示す。
- コードから直接確認できる事実と、そこから推測される影響を区別する。

### 推奨対応

「修正する」「設計を見直す」といった抽象的な提案で終わらず、どの責務をどこへ移すのか、何を検証するのか、どのインターフェースを見直すのかを示してください。仕様の決定や大規模な設計変更が必要な場合は、実装方針を確定せず、選択肢と影響を提示してください。

### 重複と継続

- 同じ根本原因から複数の問題が発生している場合は 1 つの指摘にまとめ、1 つの指摘に複数の独立した問題を詰め込まない。
- `docs/review/README.md` の未解決事項に載っている問題は、その番号（I-1、D-1 など）を併記し、「継続」「解消」「状態が変わった」のいずれかを明記する。解消済みの問題が再発していないかも確認する。

---

## 7. 要確認事項の扱い

実装とドキュメント、または設計方針の間に矛盾があり、Claude だけでは判断できない事項を記録してください。各項目には、確認した事実、判断できない理由、考えられる解釈や選択肢、それぞれの選択肢による影響、人間が判断するために必要な情報や質問を書いてください。

要確認事項を確定したバグとして扱わないでください。判断を保留したまま、ドキュメントに確定仕様として書き込まないでください。

## 8. 成果物

### 8.1 レビュー記録のファイル

`docs/review/YYYY-MM-DD.md` を新規作成し、冒頭に次のメタ情報を書いてください。

- 対象コミット範囲（前回のハッシュと今回の HEAD のハッシュ、コミット数）
- 確認した範囲（読んだドキュメント、読んだソースの範囲、読まなかった範囲とその理由）
- ビルドとテストの実施状況（実施したか、結果、実施できなかった理由）

続けて、次の節を順に書いてください。

#### 今回の変更点

| 対象 | 変更内容 | 影響 | ドキュメント反映 |
| --- | --- | --- | --- |
| `...` | ... | ... | 済 / 不要 / 要確認 |

変更が確認できなかった場合は、その理由を明記してください。変更内容は単なるファイル差分ではなく、機能・仕様・設計への影響を簡潔に説明してください。

#### ドキュメント更新内容

| 対象 | 更新内容 | 更新理由 |
| --- | --- | --- |
| `README.md` | ... | ... |
| `docs/...` | ... | ... |

更新しなかったドキュメントについても、更新が不要だったのか、判断を保留したのかを区別してください。

#### コードレビュー

重要度の高い順に、概要を表にまとめてください。

| 番号 | 優先度 | 分類 | 対象 | 問題の概要 | 推奨対応 | 未解決事項との関係 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Critical | 実装 | `...` | ... | ... | 新規 / I-n 継続 |

表の後に、指摘ごとの詳細（根拠、発生条件、影響、推奨対応）を書いてください。指摘が無い場合は、問題が無いと断定せず、確認した範囲と、指摘が見つからなかったことを書いてください。

#### 要確認事項

第 7 節の形式で一覧化してください。

#### 設計上の所感

現在のアーキテクチャと主要な責務分担、設計上の良い点、現在の懸念、今後の拡張や保守で問題になりそうな部分、今後検討する価値のある改善事項を簡潔にまとめてください。確定した問題、将来的な懸念、単なる改善候補を区別し、一般論ではなく CakeEngine の実装に基づいて説明してください。

### 8.2 未解決事項の一覧の更新

`docs/review/README.md` を更新してください。

- 「レビュー記録」の表に今回の記録を追加する。
- 「未解決事項」の各項目について、状態（継続、解消、状態が変わった）を今回の HEAD で確認して更新する。解消したものは「解消済み」の表へ移す。
- 今回新しく見つかった問題と要確認事項を、番号を振って追加する（実装の問題は I-、設計上の要確認は D-、情報は N-）。
- 冒頭の「時点」のハッシュを今回の HEAD に更新する。

### 8.3 作業の最後に報告すること

チャットでの最終報告には、作成・更新したファイルの一覧、Critical と High の指摘の要約、人の判断が必要な要確認事項の要約、ビルドとテストの実施状況を書いてください。詳細はレビュー記録に書き、報告では繰り返さないでください。

## 9. 作業上の制約

- コードから確認できない仕様を作らない。
- ドキュメントと実装が異なる場合、どちらかを勝手に正解としない。
- 明確な根拠のない改善提案を「問題」として扱わない。
- 既存設計との整合性を最優先する。
- 変更がないものについて、無理に変更点を作らない。
- レビュー対象を確認できなかった場合は、その旨を明記する。
- 重要な判断には、対象ファイルやコード上の根拠を示す。
- ビルドやテストの結果を捏造しない。実行していないビルド・テストを実行済みとして報告しない。
- 不明な仕様を確定事項としてドキュメントに反映しない。
- 運用設定で許可されていない限り、ソースコードとソース内コメントを修正しない。コードレビューで問題を発見しても記録にとどめる。
- ドキュメントの更新は必要な範囲に限定し、無関係なファイルや設定を変更しない。
- 既存のドキュメントとレビュー記録を確認し、同じ内容を不必要に重複させない。
