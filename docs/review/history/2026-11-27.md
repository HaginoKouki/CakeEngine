## 要確認事項
1. `eb6b7a7` のコミットメッセージが挙げる `UploadQueue`、`Engine/Asset/Core/`、`SoundManager` の PCM 再生はリポジトリに入っていません（Medium 3）。別ブランチや未コミットの作業があるのか、メッセージの誤りなのかを確認してください。計画書のフェーズ 1 の手順 7（`UploadQueue`）と手順 8 の `GraphicsDebugWindow` は未着手と判断しました。
2. `CakeEngine.Common.props` が Release 構成にも警告のエラー扱いを設定しています（Low 7）。意図した変更なら InternalDesign.md の記述（今回「どちらの構成でも」に合わせました）のままで、Debug だけのつもりなら props に構成の条件を付けます。
3. `SrvManager::Allocate` が尽きたときの `TextureManager` の振る舞い（High 1）。計画書 8 章は「常駐の Error テクスチャの番号を使う」としていますが、`errorTexture` 自身の番号を共有するか、読み込み失敗として `errorTexture` のハンドルを返すかは実装で決める必要があります。
4. `AssetDatabase.cpp` と `LocalId.h` の「仕様書 12章」（Low 4）。第 2 版の章番号に直すか、計画書の版が変わっても壊れないよう章番号を書かない形にするか。
5. `ProjectSettings.json` の `windowTitle` と `startupScene` は課題の提出用の値になっています。提出が終わった後に既定値へ戻すかどうかは判断が要ります。
6. 前回からの継続: Stop 後の 1 フレームの `Update`、60 FPS 固定の設定、スプライトの Scene ビューでの扱い、`Time::initialTime_`、`SpriteTesterComponent` の扱い、粒の上限、`startSpeed` の意味、`Sky.png` の要否、`ReadProperty` の `Int`、`Math/` の相対パス include、Inspector の見出し「TransformCoord」。いずれもコード上の変化はありません。

### アーキテクチャ
今回の 16 コミットは計画書 `docs/plans/AssetSystem.md` のフェーズ 1「土台」をほぼ順番どおりに進めたものです。計画書が先にリポジトリへ入り、JobSystem（手順 4）、`DeferredReleaseQueue` と `CommandManager` のフェンス値（手順 5）、`SrvManager` の空きリスト化と ImGui のコールバック直結（手順 6）、`CakeEngine.Common.props`、Tests、`Tests.yml`、`CheckLayerIncludes.yml`（手順 8 の一部）が実装されました。未着手は `UploadQueue`（手順 7）、`GraphicsDebugWindow`、`TextureManager` を空きリスト経由にする仕上げ（手順 6 の後半と手順 9）です。層の構成は変わらず、Platform 層に `Job/`、Graphics 層に `IndexFreeList` と `DeferredReleaseQueue` が加わりました。これまで「実装からは決められない」としていた Render 層と Scene 層の上下は、計画書が Scene を上と決め、CI の例外一覧がその暫定状態を固定しています。

### 良い点
計画書に「D3D12 を知らない部分を切り出してテストする」と書いた方針が、`IndexFreeList` と `DeferredReleaseQueue` でそのとおりに実現され、`Tests.vcxproj` が「テスト対象の `.cpp` を直接並べ、上の層を呼べばリンクで失敗する」形で層の検査も兼ねています。`CheckLayerIncludes` の例外一覧は issue.md の「設計規則の違反」と同じ内容を機械で守る形になり、解消済みの行が残っても失敗する設計のため、一覧が実態から離れません。`JobSystem` は「ワーカーは作業だけ、アセットと GPU に触るのは完了処理だけ」という決まりを API の形（`Submit` の 2 つの関数、`PumpMainThread`）で表しており、`WaitFor` が通知を取り逃がさない作りと `Shutdown` の順序も計画書と一致します。計画書の変更（JobSystem の置き場所、`IndexFreeList` の分離）が同じコミットで書き戻されている点も、設計書と実装を一致させる運用として良い習慣です。

### 懸念
(1) `SrvManager::Allocate` の失敗を「`assert` で止める」から「無効値を返す」に変えたことで、戻り値を見ない既存の呼び出し元（`TextureManager`、`SceneRenderTarget`）は、Debug でも止まらずにヒープの外へ進むようになりました（High 1）。API の失敗の表し方を変えるときは、呼び出し元を全部洗う必要があります。(2) `JobSystem` は完了処理が空の場合を想定しておらず、API の形（`std::function` を受け取る）が許す使い方で落ちます（Medium 2）。利用者がまだ無い今のうちに決めておくと安全です。(3) コミットメッセージが差分より多くを語っています（Medium 3）。履歴を頼りに設計書を更新する運用では、メッセージの正確さが設計書の正確さに直結します。(4) `CakeEngine.Common.props` は設定のずれを防ぐためのものですが、vcxproj 側の重複を消していないため、まだずれ得る状態です（Low 7）。

### 今後問題になりそうな部分
`DeferredReleaseQueue` は「`EndFrame` の時点で GPU が待ち切られている」同期設計の上では必ず 1 フレーム後に解放されますが、`UploadQueue` が入ってフレーム途中に `ExecuteAndWait` が無くなり、さらに描画を複数フレーム重ねる構成になると、`GetCompletedFenceValue` の進み方が変わります。計画書は「中身だけを差し替える」としていますが、`CloseFrame` に渡す値を「最後に Signal した値」にしている現在の形は、Signal の回数が増える構成で見直しが要ります。`SrvManager` の容量 4096 は仮の値で、`TextureManager` が番号を解放しない現状では、テクスチャの読み直しが入るまで使用数は増える一方です。`kJobCompletionBudget` の 2 ms も仮の値で、どちらも手順 9 の計測待ちです。

### 今後の拡張に向けて検討すべきこと
(a) `SrvManager::Allocate` の呼び出し元 3 箇所の失敗時の扱いを決め、`TextureManager` を直す（High 1）。(b) `JobSystem::Submit` の空の完了処理の扱いを決める（Medium 2）。(c) `eb6b7a7` のメッセージにある未コミットの作業の有無を確かめる（要確認 1）。(d) `CakeEngine.vcxproj` の重複設定を props に寄せ、Release の警告の扱いを決める（Low 7）。(e) フェーズ 1 の残り（`UploadQueue`、`GraphicsDebugWindow`、手順 9 の計測）に進む前に、`.github/layer-include-exceptions.txt` と issue.md の対応を保つ運用を続ける。
