## 設計上の所感

### アーキテクチャ
スプライトは「データのみのコンポーネント（Scene）→ System が DrawList に積む（Scene）→ Pass が並べ替えて `Renderer` に渡す（Render）」の形で、ギズモと同じ分け方に揃えられた。Asset 層がスプライトごとにマテリアルを持っていた旧 `Sprite` クラスが消え、Asset 層が描画物を持たなくなった点も層の役割に合う。60 FPS 固定は Platform 層の `Time` に閉じ、`Application` は `EndFrame` を呼ぶだけで済んでいる。前回の Critical（Object3D シェーダー）は解消し、法線行列は「C++ 側で逆転置を計算して送る」方式に決まった。

### 良い点
スプライト 1 枚分のデータを VS の `b0` にまとめてマテリアル無しで描く判断は、スプライトの数だけマテリアルが増える旧設計の問題を解いている。基準解像度の正射影を使うため、Game ウィンドウの描画先と Release のレターボックスの両方で同じピクセル座標が使える。テクスチャ未設定なら白、参照切れならエラーテクスチャという使い分けは「欠損が見える状態で動く」方針どおり。`ResolveSceneAssets` の拡張も既存の流れに乗せている。`SpriteRendererComponent` のヘッダコメントは、座標系、サイズの決め方、反転と切り出しの関係まで書かれていて、初見でも仕様が追える。

### 懸念
(1) `Time` の `Request` 化で、エディタの Play、Pause、Stop と `Time` の間に 1 フレームの遅れができた。Step は動くが、Stop は復元直後に 1 フレーム動く（High 1）。(2) 60 FPS の固定値が `Time` の中に埋まり、設定でも API でも変えられない（Medium 2）。(3) `TransformationMatrix` が 3 行列になったが、エンジンの `Standard` は 2 つしか読まない。ゲーム側の `Object3D` のためにエンジン共通の構造体を広げた形で、`CameraForGPU`（b2）と同じく「エンジンの構造体がゲーム側シェーダーと対で決まる」状態が増えた。

### 今後問題になりそうな部分
スプライトが 3D と同じ `TransformComponent` を使うため、Scene ビューの選択ギズモ、ImGuizmo、親子付けが「ピクセル単位」を知らない。2D 用の編集手段が無いと、配置は Inspector の数値入力に限られる。スプライト 1 枚が `FrameConstantBuffer` を 256 バイト使うので、モデルと合わせて 1 フレーム 4,096 描画で枯渇する（Low 6 と同じバッファ）。

### 今後の拡張に向けて検討すべきこと
(a) `PlayModeController::Tick` を `Time::Tick` より前に呼ぶ（`Application::RunFrame` で `Platform::BeginFrame` の前にエディタの前処理を挟む）か、`Request` を即時反映に戻す。(b) `targetFrameRate` を `ProjectSettings` か `Time` のセッターに出す。(c) スプライト用の 2D ギズモ（矩形とピボット）を `GizmoSystem` に足すか、Scene ビューに 2D モードを設ける。(d) `Standard` にも鏡面反射を入れるなら、そのときに `TransformationMatrix` の 3 行列を `Standard.hlsli` に移し、`Object3D` と共有する。
