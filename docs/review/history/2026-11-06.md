## 設計上の所感

### アーキテクチャ
今週は既存コードの整理が中心で、新機能の追加はなかった。数学ライブラリは「型は型のヘッダ、計算は `Math` 名前空間」という分け方に揃い、呼び出し側は `Math::Normalize(v)` の形で統一された。ImGui と ImGuizmo は `externals/imgui/` 配下の静的ライブラリに移り、`CakeEngine.vcxproj` から外部ライブラリの `.cpp` が消えた。SRV ヒープは `Reserved` の固定番号から `SrvManager` の順次払い出しに変わり、`TextureManager`、`SceneRenderTarget`、`ImGuiManager` が同じ入口で番号を受け取る形になった。前回までの High「Multiply のフォールスルー」と Low「HackGen のライセンス」は解消した。

### 良い点
計算関数をフリー関数にしたことで、`Vector3::Transform` が `Cake::Transform` と衝突していた問題が名前（`TransformCoord`）で解け、`constexpr` 化で内積や転置がコンパイル時にも使えるようになった。`SrvManager` は「予約枠の定数を各クラスが知っている」状態をなくし、ImGui 1.92 以降のバックエンドがテクスチャごとに SRV を要求する仕様にも、コールバックで自然に対応できた。静的ライブラリ化で外部ライブラリの警告抑制が `imgui.vcxproj` 側に閉じ、エンジン本体の `vcxproj` が読みやすくなった。これらの変更は、設計書（GraphicsLayer.md、EditorLayer.md、InternalDesign.md）を同じコミットで更新している。

### 懸念
(1) 大規模な改名の副作用として、UI の文字列まで置き換わった箇所がある（Medium 1）。機械的な置換の後に `grep` で文字列リテラルを確認する習慣があると防げる。(2) `Math/` だけ include の書き方が規約から外れ、同じフォルダ内でも揺れている（Low 4）。規約と実装のどちらを直すかを決めないと、次に Math を触る人が迷う。(3) `SrvManager` と `TransformCoord` は、失敗時の検出を `assert` に寄せている。Release 構成では検査が消えるため、「読み込み失敗で落とさない」というエンジンの方針と、Release で黙って範囲外へ進む振る舞いの間に差がある（Low 2、Low 3）。

### 今後問題になりそうな部分
`Quaternion` は API が整ったが、エンジン内に利用者がなく、`Transform::rotate` はオイラー角のままである。回転補間やカメラの姿勢に `Quaternion` を使い始めるときに、`Transform` との変換（`FromEuler` と `ToEuler` の軸順）が `Matrix4x4::MakeRotationMatrix(Vector3)` の順（X → Y → Z）と一致しているかを確認する必要がある。`SrvManager` は解放を持たないため、テクスチャのアンロードやシーン切り替えで SRV を作り直す設計になると、番号が増え続ける。`generation` と同じく「将来のアンロード」の設計と一緒に決めることになる。

### 今後の拡張に向けて検討すべきこと
(a) Inspector の見出しを戻し、改名の置換後に文字列リテラルを確認する手順をレビューの習慣にする。(b) `Math/` の include 規約を決める。(c) `SrvManager` に解放か再利用の仕組みを入れるかを、アセットのアンロード設計と合わせて決める。(d) `GizmoSettings` の `ImGuizmo::MODE` と `OPERATION` をエンジン側の列挙に置き換え、Scene 層と Release 構成から ImGui を外す。
